| **FEATURE-002** | The pre-push gate renders as a pipeline, and the push watches CI afterwards | — | **ACCEPTED by the founder 2026-08-02** | Founder ask: "is it possible to have it visual, like a release pipeline?". The reason it is worth more than looks: **a gate that does not run prints nothing, which looks exactly like a gate that passed** — which is how the ungated push of `fdae0e2` went unnoticed the same day (BUG-004 evidence). A banner makes absence visible. New `scripts/lib/pipeline.sh` (POSIX sh — the hook is `#!/bin/sh`) renders one line per stage with status + duration, buffers each stage and prints its output only on failure, ends in PASSED/FAILED with a tally. `pipe_note` lets a passing stage keep a fact that buffering would otherwise swallow (the semgrep `--jobs 1` retry). **Fails closed by construction**: `pipe_stage` exits rather than returning a status one of ~18 call sites could drop; `tests/pipeline/` asserts that against non-zero exit, signal kill, missing binary, final-stage failure, and no scratch dir. Degrades to unbuffered rather than refusing to start when `mktemp` is unavailable — "cannot create a temp dir" is a bad reason to block a push and a worse one to allow one. `scripts/watch-ci.sh` streams the required checks after the push, detached, hard-deadlined, never touching the push exit status (`AGENT_CI_WATCH=0` opts out). **Side benefit that matters for BUG-005:** per-stage timings show `agent-activity-bound` is 19.2s of 31.4s, so the budget is now arguable rather than guessed. |
